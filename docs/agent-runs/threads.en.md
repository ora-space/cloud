# Threads: the Conversation of an Agent Run

English | [中文](threads.md)

Every Agent IssueRun has exactly one Thread. It is the online copy of the Agent session's record in
Cloud and the place where the user keeps talking to the Agent: the session records the Node produces
stream into Cloud one by one as Thread entries, and messages the user appends in the Thread are handed
to the Agent as new user turns. The session JSONL saved with the Revision when the session ends is the
archive; the Thread is the live view. The run's overall lifecycle is in [Agent IssueRuns](issue-runs.en.md).

## Entries

Thread entries live in `thread_entries`, each with a Cloud-allocated sequence number `seq` that is
consecutive within the run:

| `source` | `kind` | Origin |
|---|---|---|
| `system` | `user_turn` | The first prompt, rendered by Cloud at session start from the context snapshot fixed when the run was created (the Issue, the task, context references and resume information) |
| `user` | `user_turn` | A message the user appended in the Thread |
| `node` | `meta`, `update`, `turnEnded`, `agentSwitched`, `handoffDelivered`, `gap` | The Node's session records; `kind` is the record's own type tag |

- **Cloud does not parse the business fields of session records.** The record format belongs to
  desktop's `ora-history`; Cloud only reads the top-level type tag and checks it against the known set.
  An unknown tag rolls back the whole takeover batch instead of letting Cloud invent a type. Records are
  stored as they are, at most 256 KiB each.
- `seq` is Cloud's conversation order and has nothing to do with Node sequence numbers, SSE events or
  execution IDs. The Node execution ID and Node sequence stored with an entry are internal and never
  appear in public documents.

## User turns

Every input handed to the Agent is a user turn, with a `turnId` generated by Cloud:

```text
queued ──(the Node echoes this turn's user message)──▶ delivered
   └──(still not executed when the session ends)──▶ discarded
```

- The first prompt is written as `seq=1` in the session-start transaction, which also releases the
  session work item; later turns are appended by the user.
- Cloud also writes a Thread command `submit_user_turn{turnId, content}`. When the Node echoes the user
  message as a session record, Cloud marks the matching turn `delivered` instead of appending a duplicate
  entry; the Agent's own replies and the turn's `turnEnded` carry the same `turnId` too, but they are new
  entries.
- When the session's terminal state is taken over, every turn still `queued` becomes `discarded`, and no
  later session will ever execute it.

## Appending a message

`POST .../issues/:iid/runs/:rid/thread/messages`, with an `Idempotency-Key`:

- The body's `content` is a list of content blocks, and only `{"type":"text","text":"…"}` is accepted
  today; any other block type is a client error and is never silently dropped. The decoded text totals at
  most 64 KiB; beyond that the answer is `400 content_too_large`.
- It is accepted only while the Thread is `pending`, `active` or `idle` and the run has no recorded
  cancellation request; `ending`, `ended` or a requested cancellation return `409 thread_closed`.
- A run using a personal model can only be appended to by its **initiator**
  (`403 model_run_initiator_required`); when the initiator's model connection has been revoked the answer
  is `409 model_connection_unavailable`. Any current member may append to other runs.
- The entry, the Thread state change, the Thread command and the idempotency record commit in one
  transaction. The command can be claimed by the Controller only after that commit and only once the
  session execution is registered.

## States

`issue_runs.thread_state` describes the Thread:

| State | Entered when |
|---|---|
| `pending` | The session started (the first prompt is written) and no Node record has been taken over yet |
| `active` | Any Node record is taken over, or a new user turn is written |
| `idle` | A successful `turnEnded` (not `cancelled`) is taken over and no user turn is still queued; the database time is recorded as `idle_since` |
| `ending` | The user ended it, the idle window expired or the run was cancelled, and Cloud released an `EndSession{reason}` command |
| `ended` | The session execution's terminal state is taken over, whether or not the Thread was `ending` |

When the first Node record is taken over, the run also moves from `starting` to `running`. When the
session fails (an ACP request error or an unexpected stream close) the Thread goes straight to `ended`,
and Cloud appends one failure entry carrying only a safe classification.

## Ending

There are three ways a session ends, and each only moves the Thread to `ending` and releases one
`EndSession{reason}` command; `ended`, delivery and release follow from the session's terminal state:

- **User end**: `POST .../runs/:rid/thread/end` with an `Idempotency-Key` and an empty object as body.
  While the Thread is `pending`, `active` or `idle` it returns `202` with `{"threadState":"ending"}`;
  when already `ending` or `ended` it returns `409 thread_closed`. A run using a personal model can only
  be ended by its initiator or a current administrator (`403 model_run_end_forbidden`).
- **Idle expiry**: `idle` for longer than `issue_runs.thread_idle_timeout` (15 minutes by default). The
  comparison happens entirely in the database; neither Cloud's, the Controller's nor the Node's process
  clock takes part in the decision.
- **Run cancellation**: the run has a recorded cancellation request. A cancellation request takes
  precedence over idle expiry; when both hold at once the session ends as `cancelled`.

For all three reasons the Node stops the Agent, finishes writing the session record and then ends the
session execution with a terminal state.

## The Controller side

Threads flow between Cloud and the Controller through `AgentRunService` (see
[Controller integration](../runtime/controller-integration.en.md)):

- `TakeOverThreadEvents` takes over a session execution's Node records in batches (1 to 64 records). The
  sequence must continue exactly where the last takeover stopped; a repeated record must match its
  original receipt byte for byte, and a gap or a rewrite stores nothing at all. Business transitions apply
  only to the records stored by this call and commit in the same transaction.
- `ClaimThreadCommands` claims undelivered commands in run and queue order, returning only those whose
  session execution is registered, unfinished and on a sandbox of the current generation;
  `RecordThreadCommandDelivered` records that a command reached this session execution. Commands are
  durable, so losing a `ThreadCommandAvailable` signal only delays the claim.

## Reading and live refresh

`GET .../issues/:iid/runs/:rid/thread` returns one window of the Thread:

- `after={seq}` and `before={seq}` are mutually exclusive, and with neither the tail window is returned;
  `limit` defaults to 200 with a maximum of 500; whatever the direction, results are in ascending `seq`.
- The response carries `threadState`, `idleSince`, the window's `nextCursor` and `prevCursor`, plus the
  initiator, a nullable model summary and whether the current caller may append and end (`canAppend`,
  `canEnd`).
- Authorization is the same as for reading Issue comments: any current member may read it.
- Entries are append-only, so a client that keeps reading with `after` from the highest `seq` it has seen
  neither misses nor repeats one; there is no cross-request snapshot guarantee.

When a Thread changes, the Space's SSE stream emits `issue_run.thread_appended` (entries were appended)
or `issue_run.thread_changed` (anything in the Thread's REST representation changed, including commits
that only change state). Both are only hints, and their `lastSeq` is a high-water mark, not a cursor; one
transaction emits at most one `thread_changed` per run (see
[SSE invalidation stream](../core/http-api.en.md#sse-invalidation-stream)).
