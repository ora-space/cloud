# Database Migrations Module

[中文](README.md) | [English](README.en.md)

This module contains Ora Cloud's linear, forward-only PostgreSQL schema migration catalog. Migrations are embedded directly into the Go application binary using `embed.FS` and applied deterministically by `cloudctl migrate`.

## Migration catalog

Migrations are executed in ascending numerical sequence. The sequence is **append-only**: `0001–0007` is the upstream baseline (byte-identical to `upstream/main`, never modified), `0008–0012` are the local Issue migrations, and `0013` onward are follow-up compatibility migrations.

- **`0001_core.sql`** (upstream): Foundational domain schema:
  - Identity & Access: `users`, `user_identities`, `tenants`, `tenant_memberships`, `credential_refs`.
  - Projects & Workspaces: `projects`, `project_storage`, `workspaces`, `workspace_worktrees`, `tasks`.
  - Execution runtime: `sandbox_instances`, `workspace_nodes`, `sessions`.
  - Control plane: `effects`, `operations`, `tickets`, `controller_leases`, `idempotency_keys`.
  - Invariants: Partial unique index `one_main` ensures at most one active `main` workspace per project. Foreign keys strictly enforce tenant and owner containment across all hierarchy tiers.
- **`0002_aggregate_guards.sql`** (upstream): Concurrency and mutual exclusion guards:
  - Prevents concurrent lifecycle mutations on the same project aggregate.
  - Ensures soft-deleted ancestors prevent active child state transitions.
- **`0003_resource_versions.sql`** (upstream): Optimistic concurrency controls:
  - Enforces `version` incrementing rules across mutable entities (`projects`, `workspaces`, `tasks`, `nodes`, `operations`).
  - Guards against lost updates in concurrent API operations.
- **`0004_effect_intent_and_ticket_scope.sql`** (upstream): Execution intent and ticket constraints:
  - Enforces strict scoping of execution tickets to active workspace nodes and valid admission epochs.
  - Binds durable effect declarations to specific operation phases.
- **`0005_gateway_auth.sql`** (upstream): Gateway authentication tables (accessed at runtime only by `cmd/gateway`):
  - `gateway_login_attempts`: one-shot login attempts; stores only SHA-256 digests of the attempt secret and `state`, rejects absolute, `//` and `/\` `return_to` values at the database layer, bounds the lifetime to one hour, and uses `consumed_at` to guarantee at most one session per attempt.
  - `gateway_sessions`: browser sessions; stores only the token digest, requires a non-null `expires_at` no later than 90 days after creation, keeps revocation time and the bounded `revoked_reason` together, and indexes identity revocation and bounded cleanup.
- **`0006_collab_spaces.sql`** (upstream, byte-identical to `upstream/main`): Collaboration Space schema:
  - `collab_workspaces`: tenant-scoped collaboration and visibility boundary (name, immutable slug, archive time, optimistic version). Archiving is a soft delete and does not release the slug: `UNIQUE(tenant_id, slug)` covers live and archived rows alike.
  - `collab_workspace_members`: members with roles (owner/admin/member), status (active/disabled), and optimistic version.
  - Strictly separated from the runtime `workspaces` table (Runtime Workspace, execution environments).
- **`0007_project_space_scope.sql`** (upstream, byte-identical to `upstream/main`): Project-to-Space association (**upstream semantics: mandatory**):
  - Creates a default Space (slug=`default`) for every existing tenant, including deleted tenants that still own projects.
  - Adds existing active tenant members to the default Space (admin maps to owner, member maps to member).
  - Adds `projects.space_id uuid NOT NULL` and binds every existing project to its tenant's default Space.
  - A composite foreign key `(space_id, tenant_id) REFERENCES collab_workspaces(id, tenant_id)` rejects cross-tenant ownership at the SQL level, and the `project_space_list(space_id, id)` index supports listing Projects by Space.
- **`0008_issues.sql`**: the `issues` (board) base table (formerly `0006_issues.sql`; forward-renumbered in the migration reconciliation so upstream `0001–0007` stay byte-identical).
- **`0009_issue_extensions.sql`**: `issue_statuses`, `issue_comments`, `labels`, `issue_labels`, `issue_subscribers`, `issue_views` + `issues` ALTERs (`number`, `properties`, status format check). (formerly `0007_issue_extensions.sql`)
- **`0010_issue_collaboration.sql`**: `issues` ALTERs (`assignee_type`/`assignee_id`/`project_ref` + backfill), `issue_comments` ALTERs (`parent_id`/`author_type`/`author_id`/`seq` + backfill + `UNIQUE(issue_id,seq)`), new tables `issue_runs`, `issue_activities`, `issue_context_refs`. (formerly `0008_issue_collaboration.sql`)
- **`0011_issue_interactions.sql`**: new table `issue_interactions` (the `@` interaction spine) — one row per selected collaboration target: `id, tenant_id, issue_id, comment_id, target_type, target_id, mode, task, run_id, created_at`. (formerly `0009_issue_interactions.sql`)
- **`0012_issue_interaction_input.sql`**: one generic additive column: `ALTER TABLE issue_interactions ADD COLUMN input jsonb NOT NULL DEFAULT '{}' CHECK (jsonb_typeof(input)='object')` — the confirmed form values. Deliberately excludes `version`, a `status` enum, `confirmed_at` and a separate inputs table; `0011` is not modified. (formerly `0010_issue_interaction_input.sql`)
- **`0013_project_space_optional.sql`** (append-only compatibility migration): `projects.space_id` back to **NULLABLE** — upstream `0007` imposed `NOT NULL` + full project binding; the product decision (PS3 / D2=C) keeps a Space an *optional* grouping. `0013` only relaxes the constraint; it deliberately **does NOT unbind** the projects `0007` already assigned to their default Space (no data change, no scope shrink).
- **`0014_clone_coordination.sql`** (append-only, after upstream `0008–0013`): clone coordination through the internal control contract (independent of the Effect-level `operations` model):
  - `clone_requests`: work Cloud accepted in its own business transaction, idempotent on `(tenant, user, request_id)`, state `queued→dispatched→succeeded/failed`.
  - `clone_executions`: executions a Controller registers before dispatching (exactly one per request, Controller-chosen opaque identities), their input, terminal result and the lease epoch at registration.
  - `clone_event_receipts`: exact receipts `(execution, sequence, event)` of Node events, the only basis for acknowledging a Node.
  - `control_submissions`: identity, request digest and recorded response of every state-changing submission; the same identity with the same content replays the response instead of reapplying.
- **`0015_plugins.sql`**: Adds the plugin catalog, per-space selections and runtime installation records.
- **`0016_workspace_runtime_follows_node.sql`**: Retires storage/worktree provisioning and uses independent Workspace data, Node and clone initialization. Historical records remain readable.
- **`0017_tenant_membership_and_join.sql`**: Consolidates one space per tenant with tenant membership as the sole authority; restores mandatory project space association, reserves slugs globally even after archiving, and adds durable IDaaS identity association, invitation and join-request records. Incompatible test data with multiple spaces, unscoped projects, reused slugs or divergent tenant and space names must be rebuilt; the migration never silently splits or renames data.
- **`0027_workflows.sql`** (append-only, workflow editor port): the workflow graph document `workflows` — the whole tenant-owned graph (`graph jsonb`: nodes / edges / viewport / annotations / global variables). Deliberately one table and one graph column: the graph is a document, not a relational aggregate, so there are no per-node or per-edge tables and no draft/published split.
- **`0028_workflow_snapshots.sql`**: immutable versioned captures, `workflow_snapshots`. Publishing freezes the live graph into a row under the next per-workflow version; restoring writes a chosen snapshot back over the live graph. Snapshots are append-only — an edit never rewrites one.
- **`0029_workflow_runs.sql`**: `workflow_runs`, one execution against one frozen snapshot. The run viewer needs only the snapshot graph (the canvas) and per-node states (the coloring); the graph itself is read through `snapshot_id` from `workflow_snapshots.graph` rather than copied. Cloud has no workflow engine: a created run stays `pending`, and only development fixtures explicitly wired through `Store.WorkflowRunSimulator` advance it — the same "never claim real work ran" convention as `issue_runs`.

> Numbering note: these three were `0014–0016` and collided with upstream's same-numbered migrations (`0014_clone_coordination` / `0015_plugins` / `0016_workspace_runtime_follows_node`), so merging `upstream/main` moved them to `0024–0026` per the append-only rule. Upstream then added its own `0024_agent_run_control_plane` / `0025_agent_control_integrity` / `0026_run_runtime_control`, so they moved once more to `0027–0029`, after `0026`. `schema_migrations.version` is the **full file name**, so every rename changes a migration's identity: a database that already applied the old names must be rebuilt or have `schema_migrations` updated by hand, otherwise `CheckSchema` refuses to boot with "embedded migration is missing".

## Checksum integrity and immutability

- **`schema_migrations` table**: Tracks applied versions, their SHA256 checksums, and application timestamps (`version`, `checksum`, `applied_at`). **`version` is the full filename** (e.g. `0010_issue_collaboration.sql`), so renaming an applied migration changes its identity and breaks existing databases — once applied, a migration must never be modified; add a new file instead.
- **Server startup check**: At startup, `cmd/server` runs `store.CheckSchema`, verifying that:
  1. All embedded `.sql` migration files exist in `schema_migrations`.
  2. The SHA256 checksum of each embedded file matches the recorded checksum in the database.
  3. No unknown or extraneous migration versions exist in the database.
  If any mismatch or unapplied migration is found, the server terminates immediately.
- **No AutoMigrate**: The production server daemon **never** executes DDL or modifies table structures at startup. Migrations must be applied using `cloudctl migrate` under dedicated database administrator credentials.

See [core overview](../README.en.md), [cloudctl CLI](../../../cmd/cloudctl/README.en.md), and [Core contract](../../../docs/core-contract.md).
- **`0015_plugins.sql`** (append-only): the plugin marketplace's three tables plus enum widening:
  - `plugin_sources` (deployment-global source, default `official` namespace), `plugin_catalog_entries` (catalog snapshot; reads never leave the database), `space_plugins` (authoritative per-space selection, `UNIQUE(space_id, source_namespace, identifier)`), `workspace_plugin_instances` (fan-out execution facts with tenant/owner/project/workspace composite foreign keys).
  - Widens `operations.kind` (+install_plugin/remove_plugin), `operations.step` (+plugin), `external_effects.kind` (+plugin_ensure/plugin_delete); the original CHECKs live in 0001 (PG names them table_column_check), dropped and rebuilt with the extended sets.

## 0033: Revision resume

0033 follows 0032 and lets a new run resume its Issue's latest Revision (issue-run resume decision): `revisions` gains `prior_revision_id` (the Revision a run resumed), `bundle_revision_id` (a resumed run that added nothing stores no bundle and names the row holding it, always one hop), and `resume_refused_at` with `resume_refused_reason` (a restore found the base commit gone from the remote; only `prior_revision_base_unavailable`); `issue_runs` gains `resume_revision_id` (the prior Revision fixed at session start). The anonymous `revisions_check` is replaced by the named `revisions_bundle_shape`: existing rows still satisfy the two original shapes, and the new third shape only admits a reused bundle with a prior. Purely forward and retry-safe; the new columns are NULL on existing rows. Fresh-database, upgrade and repeated-migration evidence is `TestMigration0033RevisionResumeAppliesFreshAndUpgrades` in `integration/migration_upgrade_path_test.go`; the constraints' refusal of real rows is in `integration/agent_run_resume_test.go`.

All three `0033` files retain their complete filenames and original SQL. The complete filename and checksum identify a migration; the numeric prefix is not a unique key. Fresh databases apply all three additions in filename order. An acceptance database that has already applied one of them only adds the ones missing, without rewriting its ledger or model bindings.

## 0033: User Git credentials

0033 follows 0032 and adds two columns to `credential_refs` — `name` (a 1–120 character display label, defaulting to the empty string) and `revoked_at` (the audit instant at which the owner withdrew the credential) — for user-managed personal HTTPS Git credentials (identity-access 20261010 D1/D2/D5). The credential's authority remains `tenant_id` + `owner_user_id` + `repository_scope` + `capabilities`; `name` is shown and authorizes nothing. Revocation itself is expressed by `availability='invalid'`, and `revoked_at` is the timestamp beside that state rather than a second source of truth about whether the credential is usable (`deleted_at` must not take on deletion semantics before those are defined, D10). Both columns are additive and nullable-or-defaulted, so the change is purely forward and retry-safe: no backfill, and existing rows keep their current meaning untouched. Fresh-database, upgrade and repeated-migration evidence is `TestMigration0033UserGitCredentialsAddsTheOwnerFacingColumns` in `integration/migration_upgrade_path_test.go`.

## 0034: Mirror preparation

0034 adds `mirror_preparations`, recording one prefetch of the internal Git Server inside the existing `node` → `clone` transition (workspace-content-transport D6/D7). The preparation is a step inside an existing operation rather than a new operation kind: `one_project_operation` (0001) admits at most one active operation per Project, so a separate kind would serialize against the `create_workspace` operation that needs it and the two could never overlap. One row per operation, keyed by `operation_id`; `repository_url` and `pinned_ref` are snapshotted at admission rather than joined at settlement (a Project may have changed its `repository_url`); `runtime_generation` and `control_epoch` fence late results; `generation` advances per attempt; `state` is `admitting`/`dispatched`/`ready`/`failed`/`superseded`, and `ready` requires both `commit_id` and `mirror_generation`. It also rebuilds `operations_step_check` on the 0015/0016/0020 precedent, adding `mirror`. Fresh-database, upgrade and repeated-migration evidence is `TestMigration0034MirrorPreparationAppliesFreshAndUpgrades` in `integration/migration_upgrade_path_test.go`; 0035 withdraws that step again.

## 0035: The mirror is not an operation step

0035 immediately withdraws the `mirror` step 0034 added to `operations_step_check`: the step name crosses to the desktop Controller as a protobuf enum, and that Controller is not ours to change. `internal/controlgrpc/operations.go` converts the stored step with a bare map lookup, so an unrecognized name yields the zero value rather than an error and Cloud sends `OPERATION_STEP_UNSPECIFIED`; `apps/ora-controller` answers that value with `Error::Conflict` and re-claims the operation every round, so a step the Controller cannot name is a step the operation cannot leave. Nothing was deployed, so no row ever held `mirror` and the name is removed rather than left as a latent trap (contrast the retired names 0016 keeps: applied rows still spell them). The preparation itself is unchanged and still recorded in `mirror_preparations`, still inside the existing `node` → `clone` transition. Fresh-database, upgrade and repeated-migration evidence is `TestMigration0035WithdrawsTheMirrorStep`.

## 0036: The mirror preparation's claim protocol

0036 gives `mirror_preparations` the other half of a claim protocol. 0034 fixed the row's identity, its state vocabulary and `generation` as the fence, but nothing let several Cloud processes — or one after a restart — agree on who is preparing right now and when to try again, so a worker would either dispatch the same preparation twice or never retry a lost one. `lease_expires_at` and `retry_at` close that: the claim writes the attempt's binding, bumps `generation` and sets the lease in one transaction; the dispatch signs the authorization and calls C outside any transaction, which is why none of the minutes-long part is inside the claim; and the settlement accepts a result only while `generation` still holds that attempt's fence and the lease still belongs to it. A lease rather than a lock, because an attempt that dies leaves no transaction to roll back — the lease simply lapses and the next pass may claim the row; it is written with the database's clock, or a worker whose clock runs fast would steal an attempt from a slower one still working. Two CHECKs require a `dispatched` preparation to carry a lease and a settled one to carry neither a lease nor a backoff, and the partial index `mirror_preparations_claimable` covers the "unclaimed or lapsed" scan. The constraints' refusal and admission of real rows is `TestMigration0036AddsTheMirrorPreparationClaim`.

## 0037: Push requests

0037 adds `push_requests`, the Cloud-side record of one approval for one controlled remote write (push-capability-vocabulary D2/D3/D8/D9; push-execution-authority D3/D7/D8). It is its own table rather than a row on `operations`: a push is proposed by a person rather than discovered by the control plane, the authorization it carries names no operation, execution or Node, and filing it under `operations` would put it under `one_project_operation` — so one pending push approval would block the Project's provisioning operation, and a Project mid-provision would make a push unapprovable. The row is the durable decision that one identified person approved one exact write; it deliberately does not carry the signed authorization itself, because a stored bearer is a replayable one — what is stored is the authorization's identifier, which is both the name the Credential Service records consumption under and the only value the audit needs. `state` is the execution authority's three terminal states plus the Cloud-internal `dispatching`, and a row left there is a push whose outcome Cloud does not know, which is the honest reading and never a success. `pinned_ref` requires the qualified `refs/heads/` spelling and a length of 12–200; both commits are distinct, full, lowercase object names and neither may be the null object id (a delete and a create-from-nothing are refused outright by D3); `credential_ref_version` is pinned at approval time rather than resolved at dispatch time; and `authorization_id` is UNIQUE, because one request producing a second write authorization is exactly what the idempotency rules exist to prevent. The constraints' refusal of real rows is `TestMigration0037PushRequestsAppliesFreshAndUpgrades` in `integration/migration_upgrade_path_test.go`.

## 0038: The push request's observed commit

0038 adds `observed_commit` to `push_requests`. 0037 recorded *what Cloud concluded* (`state`, `result_code`) and nothing about *what was seen*, and two of the three terminal states are only meaningful beside the value they were decided from: `uncertain`/`push_attribution_unknown` means the ref already held the requested commit, which a reader cannot tell from a push that failed and left the ref untouched without the observation; and `uncertain`/`push_target_conflict` means the ref holds something nobody authorized, where that something is the whole content of the finding — a row saying only "conflict" would send an operator to look it up by hand, and by then the ref may have moved again. So the column is stored as evidence next to the verdict rather than folded into it: Cloud derives the verdict from this value, and keeping the value is what lets a later reader re-derive the verdict instead of trusting the label. When present it is a full commit id, and it is deliberately not tied to the state — a `succeeded` row may carry it, an `uncertain` row may carry it or not, and a `failed` row may carry one too. The two combinations a CHECK coupling the column to the state would have refused are asserted against real rows by `TestMigration0038PushRequestObservedCommitAppliesFreshAndUpgrades`.

## 0039: The push dispatch lease

0039 adds `dispatch_generation` and `dispatch_lease_expires_at` to `push_requests`, because one approval can be attempted more than once and the attempt holding it has to be identifiable and bounded (push-execution-authority D6/D7/D8). The dispatch used to run inside the caller's request lifetime: a canceled request, a killed process, or a settlement whose transaction failed left the row `dispatching` forever, and no column recorded that an attempt had been made at all — so nothing could tell a dispatch still running from one that had died, and nothing could bound how often a write was re-attempted. `dispatch_generation` counts *claimed* attempts and fences their results (0 until an attempt claims the row, then 1, 2, …, with a settlement writing only while the row still holds that attempt's generation); the count and the fence share one column on purpose, since they move together by construction and a second counter would be a value that could disagree with this one. `dispatch_lease_expires_at` is written with the database's clock and a row becomes claimable again only once it has lapsed, so an attempt still in flight is never replaced; it is the reconciliation clock rather than the write fence — what stops two attempts from both writing is the executor's compare-and-swap on the authorized commit pair, and what decides whose answer counts is the generation above. `authorization_id` (0037) now names the *current* attempt's authorization rather than the only one ever minted, and its uniqueness still means what it always meant. Two CHECKs require a non-negative generation and a lease on `dispatching` rows alone, and the partial index `push_requests_dispatch_pending` covers the pass's filter and ordering. Fresh-database, upgrade and repeated-migration evidence is `TestMigration0039PushDispatchLeaseAppliesFreshAndUpgrades`.

## 0040: The mirror preparation's attempt budget

0040 adds `attempts` to `mirror_preparations`, separating the attempt budget from the fence. 0034 and 0036 gave `generation` two jobs — the fence a late result is refused against, and the count of attempts spent — and the two agree while every attempt answers but come apart when one does not: an attempt whose process is killed between the claim and the result writes nothing at all, the row stays `dispatched` at generation N until the lease lapses, and the candidate query's `generation < bound` test then refuses the row forever. The Operation sits at `node`, the Workspace sits behind the gate, and nothing works on the mirror — the wedge the attempt bound exists to prevent, reached from the other side. `attempts` counts the attempts that *concluded* (published a mirror or answered with a failure), because that is what a budget can honestly bound: a lost attempt established nothing, and the lease is what bounds it instead. `generation` stays exactly what it was, the fence. The backfill reads the only evidence the rows written before this column carry: a settled row at generation N concluded N attempts, and a `dispatched` one at generation N concluded N−1, the Nth being the attempt it is in or was left in; a `ready` row starts at zero because publishing a mirror ends the streak the budget counts, and the code clears the count on every success. The derived counts are read back after the upgrade by `TestMigration0040MirrorPreparationAttemptsAppliesFreshAndUpgrades`.

## 0041: The push request's requester is a tenant member

0041 gives `push_requests` the foreign key `(tenant_id, actor_user_id)` → `tenant_memberships(tenant_id, user_id)`. 0037 declared `actor_user_id` inline and left it without a key, while every other actor column in this schema carries one and carries this composite: `operations` and `execution_tickets` in 0001, `clone_requests` in 0014, `runtime_control_sessions` in 0019, `force_stop_intents` in 0020. The composite is the stronger statement and the one this table needs: the audit answers "which person, in this tenant, authorized this write", so a row naming a user who is no member of the tenant it belongs to does not describe a weaker approval — it cannot describe an approval at all, and a bare `users(id)` key would admit exactly that row. The column is not decorative: it is part of the identity key `(workspace_id, actor_user_id, request_id)`, and both `pushApproval` and `requirePushAccess` derive the authority to write the row from an active tenant membership, so the constraint states at rest what the grant path already enforces in code. Membership rows are never deleted — a member leaves by `status`, and no product path deletes from `tenant_memberships` — so the reference cannot be invalidated afterwards and the key cannot make an existing approval unreadable. It is the forward kind of migration: adding a foreign key validates the rows already there, and every row the product wrote already satisfies it. Both ways a requester can be a non-member, and the admission of the chain's own member, are driven by `TestMigration0041PushRequestActorMembershipAppliesFreshAndUpgrades`.

## 0034: Agent startup windows and residual ownership

Adds startup_ready_at, startup_deadline_at, startup_resume, startup_ending_deadline_at and agent_run_residuals without rewriting historical outcomes. The serialized policy scan freezes legacy active windows once. Residual ownership commits with failed/done; late true terminal facts add evidence without granting cleanup authority. Fresh/upgrade/repeat coverage: TestMigration0034StartupWindowsPreserveExistingRunOnUpgrade.
