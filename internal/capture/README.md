# internal/capture：给子进程的输出加一个上界

[中文](README.md) | [English](README.en.md)

`internal/capture` 只做**一件事**：把子进程写出来的字节留在内存里，但**不超过调用方给的字节数**；写超出的部分
被丢弃并计数，写入方**永远拿到「写完了」**。它服务于本仓库里每一条「子进程的输出由别人的仓库决定」的路径。

## 为什么需要它

本仓库启动的 Git 命令，其输出**由远端或仓库决定**：

- `git fetch` 会把远端经 sideband 发来的任意文本转发到 stderr（`remote: …` 那一类），远端想发多少就发多少。
- `git ls-remote` 会把服务端宣告的**每一个 ref** 打到 stdout，仓库有多少 ref 就有多少行。
- 命令失败时的诊断就是**远端的原话**，而远端不是可信方。

用 `strings.Builder` 接住这些流，等于把内存预算交给选择仓库的那个人，而这个进程正在跑别人的工作。这就是本包
存在的理由：这是**内存**问题，不是日志问题。

## 接口与不变量

- `Buffer{Limit}`：`io.Writer`，可以直接交给 `exec.Cmd`。保留前 `Limit` 字节，其余计入 `Dropped`。
- **写入永远返回完整长度，永远不返回错误**。这一条不是细节，而是本包最容易写错的地方：子进程的输出实际是这样
  到达 `Buffer` 的——`exec` 为管道开一个 goroutine 跑 `io.Copy`，而 `io.Copy` 把**短写当作错误**。复制一旦
  提前结束，管道读端随之关闭，写端的子进程拿到 `EPIPE`/`SIGPIPE`：于是「输出太多」变成了**杀死子进程**。
  `internal/gitserver` 早先那份实现返回的就是截断后的长度，因此任何超过 8 KiB stderr 的 `upload-pack` 都会
  因为打印太多而被自己的上界杀掉。返回原长度、丢掉装不下的部分，才让上界成为**本进程内存的性质**，而不是子进程
  的新故障模式。
- `Truncated()` / `Dropped`：**是否被截断是结果的一部分**，而不是让调用方从文本里猜。调用方需要的处置并不
  相同：日志把截断写在文本里（`String()` 末尾的 `…(N bytes dropped)`），而**事实**不能从一个被截断的流里读出
  ——所以本包只负责计数，由调用方各自决定。脱敏不属于这两类判断：调用方对**整份**捕获做脱敏，之后才按日志自己
  的窗口截断，而上界远高于那个窗口，因此能进日志的每个字节都已被脱敏，与捕获丢了什么无关。
- `Len()` 报告子进程**一共写了多少**（保留的加丢弃的），用来区分「流很短」与「流被截断」。
- `Limit` 为零时不保留任何东西——零上界的诚实读法；需要留内容的调用方自己给值。

## 本包不声称的事

- **不声称捕获完整输出**，这正是它的目的。谁需要完整内容，谁就必须为它给出上界。
- **不做脱敏**：脱敏需要知道密钥，而密钥只在调用方手里（见 `internal/cloneexec` 的 `redactFailure`）。
- **不阻止子进程继续写**：上界只管本进程的内存。被截断的流对子进程是**完全正常**的写入。

## 调用方

- `internal/gitserver`：`upload-pack` 的 stderr（`stderrLimit`，8 KiB）。
- `internal/cloneexec`：`runGit` 的两条流（`captureLimit`，64 KiB），并据此判断「截断的流不是事实」。
- `internal/mirrorpublish`：`run` 的两条流（同上 64 KiB）。

## 依赖与测试

- 依赖：仅标准库（`bytes`、`fmt`）。
- `buffer_test.go`：上界内/超出上界两种形态、`Dropped`/`Len()`/`String()` 的取值，以及**一条写入大于上界时仍
  报告完整长度、且用 `io.Copy` 搬一份超过上界的流会读完且不报错**——后者正是上面那条 `SIGPIPE` 缺陷的回归
  用例。可证伪：把 `Write` 改回返回截断后的长度，该用例立刻以 `short write` 失败。
